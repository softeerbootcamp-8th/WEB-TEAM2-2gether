# 인증 성능 개선 방향

**배경:** 부하테스트 중 로그인 API 레이턴시가 p50 1.15s/p95 1.41s/p99 1.92s로
실측됐다. 원인은 `PasswordHasher`의 PBKDF2WithHmacSHA256 반복횟수
600,000회(`1-entity.md`~`3-login-and-token.md` 구현 당시 OWASP 2023 권고를
그대로 채택한 값)가 backend 호스트(`t4g.micro`, 2vCPU)에서 CPU 바운드로
느리게 도는 것이다. 보안 설계 자체는 올바르며, 인프라(약한 CPU)와의 조합이
문제다.

## 선택지

| 방법 | 효과 | 트레이드오프 |
|---|---|---|
| 반복횟수 낮추기(예: 21만, OWASP 이전 권고치) | 즉시 ~2.8배 개선 | 보안 마진 축소, 팀 합의 필요 |
| PBKDF2 → Argon2id 전환 | 구조적으로 더 효율적, GPU/ASIC 공격에도 강함 | 메모리 사용 알고리즘이라 903MB RAM 박스에서 동시 로그인 시 새 메모리 압박 가능 — 인스턴스 업그레이드 후 검토 |
| 해싱을 전용 bounded executor로 분리 | 로그인 몰릴 때 Tomcat 워커스레드 고갈 방지(다른 API 안 끌려 내려감) | 개별 요청 체감속도는 그대로, 처리량/격리만 개선 |
| 인스턴스 업그레이드 | CPU 바운드 연산이라 코어 늘면 비례 개선 | 별도 인프라 이슈(이 문서 범위 밖) |

**권장 순서:** 해싱 executor 분리(빠르고 안전, 즉시 가능) → 인스턴스
업그레이드(별도 이슈) → CPU 여유 생기면 Argon2id 전환 검토. 반복횟수
낮추기는 보안 후퇴라 팀 동의 없이는 실서비스에 적용하지 않는다.

## 지금 당장 한 것 — 데모 프로젝트용 임시 완화

이 프로젝트는 실제 운영되는 서비스가 아니라 데모/부하테스트 목적이므로,
`PasswordHasher.ITERATIONS`를 **600,000 → 100**으로 임시 낮춰서 로그인
부하테스트 시 해싱 비용이 결과를 왜곡하지 않게 한다.

**영향받는 파일과 왜 같이 바뀌어야 하는지:**
- `backend/src/main/java/com/dbidding/account/password/PasswordHasher.java` —
  `ITERATIONS` 상수 변경.
- `backend/src/main/resources/required-data/002-user.sql` — k6 계정
  5만 개(`k6-user00001`~`k6-user50000`)의 `encrypted_password`가 600,000회
  기준으로 미리 계산돼 SQL에 박혀 있다. `ITERATIONS`만 바꾸고 이 값을 그대로
  두면 로그인 검증 시 반복횟수가 안 맞아 **k6 계정 로그인이 전부 실패한다.**
  같은 비밀번호(`K6LoadTest123!`)·같은 salt로 새 반복횟수 기준 해시를
  재계산해서 갈아끼워야 한다.
- `id=1`(`dbidding@dbidding.com`) 계정은 원래 비밀번호를 문서 어디에도
  남겨두지 않아 재계산이 불가능하다 — 이 계정의 로그인은 반복횟수를
  600,000으로 되돌리기 전까지 깨진 상태로 둔다(k6 부하테스트 대상이
  아니므로 영향 없음).
