# SLO / Error Budget 정의

**배경:** 지금까지 부하테스트 결과를 볼 때 "성공/실패"를 상태코드 하나로만
판단해서, 정상적인 가격 경합(400 최소가 미달, 409 아이덤포턴시 충돌)까지
실패로 잡히는 문제가 있었다. 또 레이턴시 목표가 엔드포인트 성격을 반영하지
않고 뭉뚱그려져 있었다. 이 문서는 엔드포인트 카테고리별 SLO와, 실패를
분류하는 기준을 정한다.

## 실패 분류 3종 (Four Golden Signals의 "Errors"를 세분화)

| 분류 | 정의 | 예시 | SLO 가용성에 포함? |
|---|---|---|---|
| 명시적 실패 | 서버가 스스로 처리 실패를 인지하고 응답 | 5xx, 예외 | **포함** — 유일한 하드 실패 판정 기준 |
| 정책적 실패 | 비즈니스 규칙에 따른 정상 거부 | 400(최소가 미달), 409(경합 충돌), 401 | **미포함** — 단, 별도 SLI로 계속 추적 |
| 묵시적 실패 | 응답은 성공(2xx)이지만 실질적으로 전달 안 됨 | SSE 브로드캐스트가 `DiscardPolicy`로 조용히 드랍됨 | 대상 메트릭 자체가 없어서 지금은 추적 불가 — [`2-metrics-gap-and-instrumentation.md`](2-metrics-gap-and-instrumentation.md)에서 계측 추가 |

정책적 실패를 가용성에서 제외하는 이유: 두 사용자가 동시에 입찰하면 시스템이
아무리 빨라도 한쪽은 거부된다 — 이건 서비스 품질 문제가 아니라 경매 구조
자체의 본질이다. 다만 "가격 정보를 늦게 뿌려줘서 낡은 가격 기준으로 입찰했다
거부되는" 경우는 실시간성 문제일 수 있어, 정책적 실패율이 경합 상황 대비
비정상적으로 튀는지는 별도 SLI로 계속 감시한다.

## SLO 윈도우

30일 rolling 같은 상시 운영 개념 대신 **부하테스트 세션 하나**를 윈도우로
잡는다. 이 프로젝트는 상시 트래픽이 아니라 세션 단위로 부하를 가하는
구조이기 때문에, "이번 세션 동안 실패율이 예산 안에 있었는가"를 보는 용도로
축소해서 쓴다.

## 엔드포인트 카테고리별 목표

세분화 기준(아래 3가지를 모두 만족할 때만 별도 카테고리로 쪼갠다):

1. 하위 항목끼리 실제로 지연/실패 양상이 다르다
2. 합쳐서 보면 한쪽 문제가 다른 쪽에 가려진다
3. 어느 쪽이 문제인지에 따라 대응 방법이 실제로 달라진다

이 기준으로 "bid-context"를 "일반조회"에서, "auction-SSE"를 "notification-SSE"에서
분리했다(각각 지연 분포와 실패 모드가 실측으로 다르게 나왔다). 정책적 실패의
원인별(400 vs 409) 세분화는 지금은 대응 방법이 같아서 보류한다.

| 카테고리 | 가용성 목표(5xx 기준) | p95 목표 | p99 목표 | 비고 |
|---|---|---|---|---|
| 인증(`/api/auth/login`, `/refresh`) | 99.9% | 500ms | 900ms | 2026-08-10 실측 p95 1.41s/p99 1.92s로 크게 미달 — PBKDF2 비용 × 인프라(t4g.micro) 문제, [`../auth/6-password-hash-cost-tuning.md`](../auth/6-password-hash-cost-tuning.md) 참고 |
| 입찰 쓰기(`POST /api/auctions/{id}/bids`) | 99%(5xx만) | 300ms | 500ms | 실측 p95 429ms/p99 719ms |
| bid-context(`GET .../bid-context`) | 99.5% | 200ms | 350ms | 실측 p95 321ms/p99 446ms |
| 일반조회(목록/상세/통계) | 99.5% | 300ms | 600ms | 실측 p95 380ms/p99 **1.52s** — 꼬리가 김, 원인 조사 필요 |
| auction-SSE 연결 수립 | 99% | 500ms | 1s | 계측 없음 — 문서 2에서 추가 후 확정 |
| notification-SSE 연결 수립 | 99% | 800ms | 1.5s | 티켓 발급 단계가 하나 더 있어 auction보다 여유를 둠. 계측 없음 — 문서 2에서 추가 후 확정 |
| SSE 이벤트 end-to-end 전달 | - | 300ms | 600ms | 지금 있는 `dbidding_auction_sse_send_duration_seconds`는 서버 `send()` 호출 자체만 재서(p99 3ms) 이 목적엔 못 씀 — 문서 2에서 클라이언트 수신 시각까지 포함한 계측 추가 후 확정 |

## 참고

- 실측치는 2026-08-10 기준, Redis 도입 전 organic 트래픽 24시간 집계다.
  세션 단위로 통제된 정식 기준선은 [`4-redis-baseline-comparison.md`](4-redis-baseline-comparison.md)에서
  별도로 잡는다.
- 로그인 목표(p95 500ms)는 업계 관행(Google RAIL, 일반적인 로그인 API
  p95 300~500ms) 기준이며, 지금 인프라로는 달성 못 한다는 걸 알고 잡은
  지향점이다. 인스턴스 업그레이드와 PBKDF2 반복횟수/알고리즘 조정이 선행
  과제다.
