# 10차 부하테스트 — 알림·지갑 SSE 병합(`/api/me/stream`) 검증 + MySQL 프로젝션 컨슈머 병목 발견

**대상 환경:** prod(`api.dbidding.shop`, RAM 1.8GiB, vCPU 2개,
`-Xmx1280m -XX:+UseG1GC -XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/app/logs/heapdump-%p.hprof -Xlog:gc*`),
`SPRING_PROFILES_ACTIVE=redis,sse-virtual-threads`, `HikariCP max=30`,
`SERVER_TOMCAT_THREADS_MAX=50`. 백엔드 컨테이너는 이 세션 시작
약 1시간 23분 전(2026-08-17T15:13:52Z)부터 떠 있었음 — 웜업 충분. 9차
(`13-round9-redis-executor-full-suite.md`) 헤더의 설정과 완전히 동일해서
(`docker inspect`로 재확인), JVM/스레드모델/풀 크기 조건에 대한 "조건이
달라졌다" 캐비어트는 이번 비교표에 필요 없다.

**작성일:** 2026-08-17.

**배경:** 9차를 포함한 이전 모든 회차는 부하테스트 중 알림 SSE(그리고
경매 SSE)만 실제로 연결했고, **지갑 SSE는 한 번도 부하테스트 트래픽에
포함된 적이 없었다.** 9차 직후 지갑 SSE를 간단히 붙여서 애드혹으로
테스트했더니 커넥션 부하가 예상보다 커서, 유저당 SSE 커넥션을 3개
(경매 + 알림 + 지갑)에서 2개(경매 + `/api/me/stream`)로 줄이는 병합
작업(#557, PR #558 백엔드 `MeSseConnectionManager` + PR #562 k6 스크립트
갱신)이 나왔다. 10차의 목적은 **이 병합된 커넥션이 표준 6종 부하테스트
세트 전체를 통해 실제로 잘 버티는지** 확인하는 것 — 이번이 지갑발
SSE 트래픽이 부하테스트에 실제로 실린 **첫 번째** 회차다. 따라서 9차는
지갑 SSE 관련 수치의 A/B 기준선으로 쓸 수 없다(9차엔 애초에 그 트래픽이
없었으므로) — 9차와의 비교는 "병합 이후 전체 부하/커넥션 관련 지표가
9차보다 나빠지지 않았는지"를 보는 용도로만 쓴다.

**⚠️ 이번 회차에서 심각한 발견이 있었음 — §4 먼저 읽을 것.** 요청
실패율/`bid_server_error`가 9차보다 훨씬 높게 나왔다. 근본 구조적
원인은 **MySQL 프로젝션 컨슈머가 단일 스레드
(`Executors.newSingleThreadExecutor`, `AuctionBidStreamConsumer.java:56-57`)라
지속 부하 아래서 따라잡지 못해 생긴 전역 503 스톰**이다. **초안에서는
이걸 SSE 병합과 "무관"하다고 썼는데, 작성 후 재검증 결과 정정한다 —
같은 구조적 결함이 9차에도 있었는데 왜 이번엔 12배 더 심했는지를
직접 대조해보니, 이번 회차에 처음 실제로 흐르기 시작한 지갑
SSE 트래픽이 vCPU 2개짜리 박스에서 이 단일 스레드 컨슈머의 CPU
경합을 유발해 악화시켰다는 증거가 나왔다(§2.3, §4.7).** 즉 "SSE
병합이 원인"은 아니지만 "SSE 병합과 무관"도 아니다 — 병합 자체(커넥션
안정성)는 §2에서 검증된 대로 문제없이 버텼지만, 그로 인해 실제로
흐르게 된 지갑 트래픽의 CPU 비용이 기존의 구조적 약점을 더 크게
드러낸 촉매 역할을 했다.

## 0. 결론 먼저

1. **SSE 병합(`GET /api/me/stream`) 자체는 목표를 달성했다.** 6개
   시나리오 전 구간에서 `dbidding_sse_connections{stream="me"}`가
   `stream="auction"`과 항상 정확히 같은 값으로 유지됐다(예:
   1000-tier 전 구간 1,001=1,001). `sse_broadcast_saturated_total`
   델타는 6개 시나리오 전체·전 구간에서 0, `dbidding_me_sse_send_failures_total`
   델타도 전체 0 — 병합된 커넥션이 끊기거나 broadcast가 밀린 흔적이
   없다. 유저당 SSE 커넥션이 3개→2개로 줄면서 우려했던 "지갑 SSE를
   실제로 붙이면 부하가 커진다"는 문제는 이번 표준 세트 기준으로는
   나타나지 않았다(§3).
2. **그런데 세션 전체의 요청 실패율이 9차보다 훨씬 높게 나왔다 —
   근본 원인은 별도의 구조적 문제이지만, 이번 회차에 악화시킨 촉매는
   SSE 병합으로 처음 흐르게 된 지갑 트래픽으로 보인다(§4.7 정정
   참고).** `GET
   .../bid-context`가 세션 측정 구간에서 총 144,073회 503을 반환했다
   (같은 API 200 성공 223,563건 대비 39.2%, 9차 11,718건의 약 12배).
   503은 `AuctionException.stateRecoveryRequired()`
   (`RedisAuctionStateSeeder.java:41-46`)에서 나오고, 이건
   `RedisProjectionCatchUpVerifier.isCaughtUp()`
   (`RedisProjectionCatchUpVerifier.java:54-77`)이 **PENDING/ERROR
   상태인 `timeline_events`가 하나라도 있으면 프로젝트 전역에서 false를
   반환**하기 때문이다. 세션 도중 DB를 직접 조회한 결과, 세션 구간
   (`occurred_at > 16:30 UTC`) 이벤트 중 `processed_at`까지의 지연이
   5분을 넘는 비율이 **89.9%**(55,805건 중 50,188건)였다 — 프로젝션
   컨슈머가 사실상 세션 내내 밀려 있었다는 뜻이다. 근본 원인은
   `AuctionBidStreamConsumer.java:56-57`의 `Executors.newSingleThreadExecutor`
   — 컨슈머가 구조적으로 단일 스레드라, 이번처럼 78분간 지속된 높은
   입찰 부하(분산 시나리오 기준 QPS50~400 계단, 초당 최대 400여건의
   입찰 시도) 아래서는 처리량이 유입량을 못 따라간다. 세션 종료
   ~5분 뒤 재확인했을 때 PENDING이 1건까지 줄어 있어(§4.3), **로드가
   멈추면 컨슈머가 스스로 따라잡긴 한다** — 영구 장애가 아니라 지속
   고부하에서의 처리량 부족이다.
3. **9차가 발견한 "핫경매집중 시나리오의 DB 락 경합 소멸"·"Hikari
   거의 안 참" 결론은 이번에도 재현됐다** — `bid-only-load
   핫경매집중`에서 Hikari active 최댓값 9/30(9차 9/30과 동일), row-lock
   경합 없음. `RedisBidExecutor`(`@Profile("redis")`) 경로가 여전히
   MySQL 락을 안 타는 구조이기 때문이다(9차 §5 원인 그대로 유효).
4. **Full GC 0회, heap dump 0건, 컨테이너 재시작 0회** — 9차와 동일.
   RAM 1.8GiB + `-Xmx1280m` 조합은 이번에도 안정적이었다(§6).
5. **pure-throughput 1000-tier에서 backend 인스턴스의 스왑아웃이
   9차보다 뚜렷이 커졌다**(§5) — QPS300~400 구간에 집중, node_exporter
   원시 카운터로 직접 재확인해 실측임을 확인했다(§5.1). SSE 병합과의
   인과관계는 확정하지 않았고, §4의 503 스톰과 함께 발생한 부수 현상일
   가능성이 있다(§7 한계).
6. **정정 2건(작성 후 사용자 검증으로 반영):** (a) §4의 503 스톰을
   "SSE 병합과 무관"으로 썼던 초안은 과했다 — 같은 250-tier
   QPS50/QPS100 구간을 9차와 직접 대조하니 `node_load1`이 1.05→2.15로
   2배였다(§4.7). 병합 자체는 안정적이었지만(§2), 병합으로 처음
   흐르게 된 지갑 트래픽의 CPU 비용이 단일스레드 컨슈머의 스케줄링
   기회를 줄여 기존 구조적 약점을 증폭시켰을 가능성이 높다. (b) 힙
   여유가 있으니 `-Xmx`를 800MB로 낮추자는 제안은 기각했다 — G1의
   Eden/Survivor/Old 3풀을 합산한 실제 committed 힙 피크는 9차
   938MB·10차 968MB로 이미 800MB를 넘어섰다(§5.2).

밖, §7).

## 2. SSE 병합(`/api/me/stream`) 검증 상세

### 2.1 커넥션 수 — `auction`과 `me`가 항상 일치

pure-throughput 1000-tier(SSE_VUS=1000, 유저당 auction+me 2커넥션,
합 2,000 커넥션 목표) 전 구간에서:

| 구간 | `stream=auction` avg/max | `stream=me` avg/max | `sse_broadcast_saturated_delta` | `me_sse_send_failures_delta` |
|---|---:|---:|---:|---:|
| QPS50 | 1,001.00 / 1,001.00 | 1,001.00 / 1,001.00 | 0.00 | 0.00 |
| QPS100 | 1,001.00 / 1,001.00 | 1,001.00 / 1,001.00 | 0.00 | 0.00 |
| QPS150 | 1,001.00 / 1,001.00 | 1,001.00 / 1,001.00 | 0.00 | 0.00 |
| QPS200 | 1,001.00 / 1,001.00 | 1,001.00 / 1,001.00 | 0.00 | 0.00 |
| QPS300 | 1,001.00 / 1,001.00 | 1,001.00 / 1,001.00 | 0.00 | 0.00 |
| QPS400 | 1,001.00 / 1,001.00 | 1,001.00 / 1,001.00 | 0.00 | 0.00 |

250-tier·500-tier도 동일 패턴(각각 251/251, 501/501 유지, 원본은
raw-data 파일 참고). **`me` 스트림이 `auction` 스트림과 한 번도
어긋나지 않았다** — 지갑/알림 이벤트가 실제로 흐르는 병합 커넥션이
경매 SSE와 동등한 안정성으로 유지됐다는 뜻이다.

### 2.2 병합 전용 메트릭

`dbidding_me_sse_send_duration_seconds_*`, `dbidding_me_sse_send_failures_total`은
PR #558로 새로 생긴 `me` 전용 계측이다(`MeSseConfig.java:12-15`,
`meSseMetrics` 빈이 `new SseMetrics(meterRegistry, "me", clock)`로
등록). 6개 시나리오 35개 구간 전체에서 `me_sse_send_failures_delta`는
예외 없이 0 — 알림/지갑 이벤트 전송 자체가 실패한 적이 없다.

### 2.3 유저당 커넥션 수 감소 효과

9차는 `notification`(약 251~1,001) + `wallet`(1~2, 사실상 미연결)로
유저당 사실상 SSE 2개(경매+알림)만 부하를 받았다 — 지갑 SSE는
연결만 됐지 트래픽이 거의 없었다. 10차는 병합 후 유저당 정확히
2커넥션(경매+`me`)이고, `me` 하나가 알림+지갑 이벤트를 모두 실어
나른다. §1 비교표의 Hikari/스왑 지표가 9차 대비 소폭 상승(Hikari
9→11, 스왑 대폭 증가)했지만, 스왑 증가는 §5.1에서 보듯 QPS300~400
구간에 집중돼 있고 §4의 503 스톰(Redis `auction:bid:idempotency:*`
키 폭증, DB 재조회 증가 등 부수 효과)과 시기가 겹친다. **정정
(작성 후 사용자 지적으로 재검증): "SSE 커넥션 자체가 원인이라고
단정할 근거는 없다"고 썼던 최초 결론은 과했다 — §4.7에서 9차와
동일 구간(250-tier QPS50/QPS100, 503 스톰이 쌓이기 전 시점)의
CPU/load average를 직접 대조한 결과, `node_load1`이 1.05→2.15로

높다.**

## 3. 구간별 + API별 상세 (서버 실측, `histogram_quantile`)

방법은 9차와 동일: `http_server_requests_seconds_bucket`을 구간 끝
시각 기준으로 `histogram_quantile(0.95/0.99, sum(rate(...[구간길이])) by (le))`로
평가. 스테이지 경계는 각 실행의 실측 로그에서 "메인 구간(bidContextReads
등)이 실제로 값을 찍기 시작한 시각"을 오프셋으로 삼아 계산했다

오프셋은 로그에서 직접 관측한 값이라 9차보다 오차가 작을 것으로

## 4. 근본원인 분석 — MySQL 프로젝션 컨슈머 단일 스레드 병목

### 4.1 규모

세션 측정 구간(35개 스테이지 윈도우) 합산으로 `GET
.../bid-context`가 반환한 상태코드:

| 시나리오 | 503 | 200 | 503 비율 |
|---|---:|---:|---:|
| pure-throughput 250 | 150 | 67,655 | 0.2% |
| pure-throughput 500 | 30,626 | 38,077 | 44.6% |
| pure-throughput 1000 | 43,156 | 24,906 | 63.4% |
| hot-auction-pattern | 6,797 | 11,200 | 37.8% |
| bid-only-load 분산 | 32,089 | 40,140 | 44.4% |
| bid-only-load 핫경매집중 | 31,255 | 41,585 | 42.9% |
| **합계** | **144,073** | **223,563** | **39.2%** |

Prometheus 라벨 전체 누적(세션 전 구간, 스테이지 경계 밖 램프업/다운
포함)으로 재확인한 값은 이보다 조금 더 크다 — `GET
.../bid-context` 200=295,858건, 503=150,709건(§실행 시점 실측
`curl`). **세션 시작 직후(250-tier)는 0.2%로 거의 없다가, 500-tier부터
누적돼 세션 내내 30~65% 수준을 유지했다** — 표 §1의 첫 실행부터
백로그가 누적되기 시작했다는 뜻이다.

### 4.2 코드 경로

1. `RedisAuctionStateSeeder.seedIfAbsent()`
   (`backend/src/main/java/com/dbidding/auction/bid/RedisAuctionStateSeeder.java:41-46`):
   Redis에 경매 상태가 콜드미스(없음)인데
   `projectionCatchUpVerifier.isCaughtUp()`이 false면
   `AuctionException.stateRecoveryRequired()`를 던진다 → 컨트롤러가
   이걸 503으로 매핑한다.
2. `RedisProjectionCatchUpVerifier.checkCaughtUp()`
   (`backend/src/main/java/com/dbidding/auction/stream/RedisProjectionCatchUpVerifier.java:66-77`):
   **엔티티(경매) 단위가 아니라 시스템 전역 상태 하나**다 — Redis
   Stream(`event:timeline`)의 최신 이벤트가 MySQL에서 `PROCESSED`로
   찍혔는지, 그리고 `timeline_events`에 `PENDING`/`ERROR`가 단 1건도
   없는지를 확인한다. 셋 중 하나라도 어긋나면 **콜드미스인 모든
   경매**에 대해 false가 반환된다(0.5초 TTL 캐시, `RedisStateSingleFlight`로
   동시조회는 합침).
3. `AuctionBidStreamConsumer`
   (`backend/src/main/java/com/dbidding/auction/stream/AuctionBidStreamConsumer.java:56-57`):
   `event:timeline` 스트림을 MySQL `timeline_events`에 순차 반영하는
   컨슈머가 **`Executors.newSingleThreadExecutor(Thread.ofVirtual()...)`로
   단일 스레드**다. 가상 스레드라 I/O 대기 자체는 안 붙잡지만, 이
   컨슈머 로직은 한 번에 이벤트 하나씩 순서대로 처리하는 구조라
   동시성 자체가 1이다 — 유입 이벤트 처리량이 이 한 스레드의
   처리 속도를 넘으면 무조건 큐가 쌓인다.

### 4.3 직접 확인 — 처리 지연 분포

세션 구간(`occurred_at > 2026-08-17 16:30:00`)에 발생한 `timeline_events`
중 `processed_at`이 채워진 55,805건의 `TIMESTAMPDIFF(SECOND,
occurred_at, processed_at)` 분포:

| 지연 구간 | 건수 | 비율 |
|---|---:|---:|
| ≤1초 | 1,734 | 3.1% |
| 1~10초 | 374 | 0.7% |
| 10~60초 | 1,090 | 2.0% |
| 60~300초 | 2,419 | 4.3% |
| **300초 초과(5분+)** | **50,188** | **89.9%** |

세션 종료(17:55:54Z) 약 5분 반 뒤(18:01:29Z) 재확인 시점의
`projection_status` 분포는 `PROCESSED=66,023건`, `PENDING=1건`
(auction_id=3001001, `bid.accepted.v1`, `occurred_at=17:50:53`,
`attempt_count=0`) — **`ERROR`는 0건**이었다. 즉 이번엔 9차(#535)처럼
poison-pill 하나가 영구히 막고 있던 게 아니라, **부하가 사라지자
컨슈머가 계속 처리해 백로그를 거의 다 비운 상태**였다 — 순수하게
"유입 > 처리 속도"인 지속 부하 문제라는 걸 뒷받침한다.

### 4.4 POST `/bids` 자체는 거의 영향받지 않았다

Prometheus 라벨 전체 누적(세션 전 구간) 기준 `POST
/api/auctions/{auctionId}/bids` 상태코드: `201=68,021`, `400=34,517`,
`409=382`, **`500=1`**. 즉 실제 입찰 승인 경로(`RedisBidExecutor`,
Redis Lua 단독)는 이 병목과 거의 무관하다 — 503 스톰은 거의 전부
`bid-context` GET의 콜드미스 케이스에 집중됐다. 사용자 체감상으로는
"입찰은 됐는데 입찰 컨텍스트 조회가 가끔 실패하는" 형태로 나타났을
가능성이 높다.

### 4.5 9차와의 관계

9차(§6, #535)는 같은 메커니즘을 poison-pill ERROR 1건이 FIFO를
영구히 막는 문제로 분석했고, 이번 세션 재확인 시점엔 그 백로그가
정리돼 있었다(§4.3, ERROR 0건). 하지만 **같은 구조적 게이트가 이번엔
poison-pill 없이도, 순수 처리량 부족만으로 재현됐다** — 9차의
결론("콜드시드 rewind로 인한 프로젝션 파이프라인 정지")은 원인 중
하나였을 뿐, `AuctionBidStreamConsumer`가 구조적으로 단일 스레드라는
게 더 근본적인 제약이었다는 뜻이다. 9차 raw data에서도 503이
11,718건 있었지만(§1 비교표) 이번의 1/12 수준이었다 — 9차는 세션
전체가 아니라 일부 구간에서만 백로그가 쌓였던 것으로 보이는 반면,
이번은 **거의 세션 시작 직후부터 끝까지** 쌓여 있었다(§4.1의
250→500-tier 급증).

### 4.7 정정 — 왜 이번엔 9차보다 12배 심했는가 (CPU 경합 증거)

**초안(§0/§2.3 최초 버전)은 이 악화를 SSE 병합과 "무관"하다고 썼다.
작성 완료 후 사용자가 "9차도 비슷한 부하를 보냈는데 왜 이번만
이렇게 나쁘냐"고 직접 반박해, 재검증했다.** 9차와 10차의 **같은
시나리오(pure-throughput 250-tier)의 같은 스테이지(QPS50/QPS100),
즉 503 스톰이 쌓이기 전인 세션 시작 직후 시점**을 Prometheus로
직접 대조했다:

| 지표 | 9차 (QPS50/QPS100) | 10차 (QPS50/QPS100) |
|---|---:|---:|
| `process_cpu_usage` | 0.213 / 0.261 | 0.265(+24%) / 0.365(+40%) |
| `node_load1` | — / **1.05** | — / **2.15**(2배) |
| `jvm_threads_live_threads` | — / 105 | — / 109 (거의 동일) |
| SSE 커넥션 | notification=251, wallet=1(사실상 미연결) | me=251(알림+지갑 병합) |

vCPU 2개 박스에서 `node_load1`이 1.05→2.15로 2배 됐다 — 아직 503이
거의 없던 시점인데도다. 스레드 **개수**는 거의 그대로(105→109)라
"스레드가 늘어서"가 아니라 "스레드당/전체 CPU 소비가 늘어서"다.
같은 시점에 유일하게 실질적으로 바뀐 건 지갑 SSE가 이번에 처음
실트래픽을 실었다는 것뿐이다(§2.3, §背景).

**결론 수정: `AuctionBidStreamConsumer`의 단일 스레드 설계가
근본적인 구조적 결함이라는 건 그대로 유효하다(9차에도 503이
11,718건 있었다는 게 그 증거) — 하지만 "이번 회차가 9차보다
12배 심한 이유"는 SSE 병합과 무관하지 않다.** 병합된
`/api/me/stream`이 지갑 이벤트를 실제로 흘려보내기 시작하면서
생긴 CPU 비용이, 이미 여유가 별로 없던 2-vCPU 박스에서
`AuctionBidStreamConsumer`의 가상스레드가 받는 스케줄링 기회를
줄였을 가능성이 높다 — 컨슈머의 폴링 쿼리 자체는 문제없다(§4.7.1
참고). 즉 **"병합 자체(커넥션 안정성)는 문제없다(§2)"는 결론과
"병합으로 실제로 흐르게 된 트래픽의 CPU 비용이 기존 구조적 약점을
증폭시켰다"는 결론은 양립한다** — 후자를 최초 버전에서 빠뜨렸다.

#### 4.7.1 기각한 대안 가설들 (참고용)

- **큐 물량 증가?** 지갑 이벤트가 같은 Redis Stream(`event:timeline`)에
  들어가는 건 `WalletStateChangedStreamEvent`(2026-08-14 도입,
  `git log` 확인) — 9차 이전부터 이미 있었다. 지갑 SSE 연결 여부와
  무관하게 입찰마다 발행되므로, 이번 회차라고 이벤트 물량 자체가
  늘어난 건 아니다.
- **폴링 쿼리 성능 저하(테이블 누적)?** `findFirstByProjectionStatusOrderByIdAsc`는
  `idx_timeline_events_projection_status` 단일 컬럼 인덱스를 쓰는데,
  InnoDB 보조 인덱스는 같은 값 안에서 PK(=id) 순으로 이미 정렬돼
  있어 `ORDER BY id LIMIT 1`에 filesort가 필요 없다(`EXPLAIN ANALYZE`로
  직접 확인, `type=ref, Using index; Extra: NULL`). 회차를 거듭하며
  누적된 전체 행 수(현재 68,031건)는 이 쿼리 비용에 영향을 주지
  않는다.
- **프로젝션이 SSE push를 직접 호출?** 아니다 —
  `AuctionBidStreamPersistenceService.java:189` 주석대로 "주문 알림과
  wallet SSE는 Redis 승인 직후 발행하고, projection은 DB 반영만
  담당한다" — 컨슈머 스레드 자체가 SSE 전송을 블로킹하지 않는다.

### 4.8 권고

- `AuctionBidStreamConsumer`의 단일 스레드 처리량을 늘리거나(배치
  처리, 여러 컨슈머로 파티셔닝 등), `RedisProjectionCatchUpVerifier`의
  "전역 단일 게이트" 설계를 "해당 경매 자체가 최신인지"로 좁히는 게
  근본 해법 후보다 — 코드 변경 범위가 커서 이 문서 범위 밖.
- §4.7의 CPU 경합 증거를 볼 때, 컨슈머 워커에 우선순위를 주거나
  (예: 전용 플랫폼 스레드 + OS 스케줄링 우선순위, 혹은 SSE
  디스패치용 executor와 물리적으로 분리된 실행 자원) 지갑/알림 SSE
  fan-out과의 CPU 경쟁을 줄이는 것도 후속 조치 후보다 — vCPU를
  늘리는 것보다 저렴할 수 있다.
- 이 발견은 SSE 병합의 "커넥션 안정성" 검증(§2) 결론 자체는 바꾸지
  않지만, 병합 이후 실운영 배포 전에 프로젝션 컨슈머 병목을 먼저
  해결하는 걸 권한다 — 별도 GitHub 이슈로 등록해 추적할 것(#535의
  연장선 혹은 신규 이슈).

| 17:19:15 | 2,265,127 |

카운터 리셋 없이 단조 증가하며, 스왑아웃이 QPS400 구간의 **마지막
30~40초에 집중적으로 몰려서** 일어난 게 원시 데이터로도 확인된다
(2,177,563→2,260,628, 약 83,065페이지 ≈ 324MB가 수십 초 안에
스왑아웃됨). `increase()`가 낸 96,198.86은 외삽 보정값이라 원시
델타(약 84,174)보다 크게 나오지만, **급증 자체는 계측 artifact가
아니라 실측**이다.

### 5.2 힙 여유 재검토 — "Xmx를 800으로 낮추면 안정화되지 않을까"는 역효과 위험

대화 중 "힙이 768MB를 넘는 걸 못 봤다, `-Xmx`를 800 정도로
낮추면 다른 데 쓸 메모리가 늘어날 것 같다"는 제안이 나왔다.
실측으로 검증한 결과 **기각한다** — G1은 힙을 Eden/Survivor/Old
Gen 3개 풀로 나눠 `jvm_memory_committed_bytes{area="heap"}`에
**풀별로 별도 시리즈**를 노출한다. 셋 중 하나만 보면 낮아 보이지만,
**세 풀을 합산한 실제 총 committed 힙**은:

| | Eden | Survivor | Old | **합계** |
|---|---:|---:|---:|---:|
| 9차 세션 최댓값 | 405.8MB | 547.4MB | 30.4MB | **≈938MB** |
| 10차 세션 최댓값 | 514.9MB | 438.3MB | 61.9MB | **≈968MB** |

둘 다 이미 800MB를 넘는다 — `-Xmx800m`은 실측 피크보다 낮은
천장이라, 얹으면 GC 압박·풀 GC 유발 위험이 있다. 논힙(Metaspace,
Code Cache 등 5개 풀 합산)도 최댓값 ≈227MB 추가로 잡혀, JVM
전체 풋프린트 피크는 힙+논힙 합쳐 **≈1.2GB**다.

**대화 중 사용자가 스스로 짚은 반론도 실측과 일치한다**: "503으로
많은 요청이 조기 반환되면, 처리량 자체가 억눌린 상태에서 잰
힙 사용량이라 프로젝션 병목을 고치면 오히려 힙을 더 쓸 수 있다."
실제로 503이 9차보다 12배 많았던 10차가 힙 committed 피크도
9차보다 높다(968MB > 938MB) — 처리 억제 상태에서도 이미 더 먹고
있었다는 뜻이라, 병목을 고쳐 실처리량이 늘면 피크가 800MB를 더
크게 웃돌 가능성이 높다.

스왑 급증 시점(17:16~17:22 UTC) 실측: `node_memory_MemAvailable_bytes`
평균 ≈126.5MB, `node_memory_Cached_bytes` ≈143.5MB,
`node_memory_MemTotal_bytes` ≈1.92GB — 메모리가 실제로 빠듯한
건 맞다. 다만 원인은 "힙을 과하게 잡아서"가 아니라 **JVM 전체
풋프린트(≈1.2GB)가 1.8GB 박스에서 차지하는 비중 자체가 크다**는
쪽에 가깝다. `-Xmx` 하향보다는 (a) 8차에서 했던 것과 같은 축의
RAM 증설, 또는 (b) 논힙/커넥션 버퍼(1000+ SSE 커넥션의 소켓·버퍼
비용 포함) 쪽 절감이 더 맞는 방향으로 보인다 — 이 문서 범위 밖의
별도 조사가 필요하다.

grep -c 'Pause Full' /app/logs/gc-1.log /app/logs/gc-1.log.0 /app/logs/gc-1.log.1 /app/logs/gc-1.log.2

버텼다.

## 7. 한계 및 다음 단계

- **hot-auction-pattern의 총 요청 수(29,749)가 9차(123,943)와 큰
  차이가 나는 원인을 이 문서에서 확정하지 못했다** — 런북 §2.2
  커맨드 그대로 `-e` 오버라이드 없이 실행했고 iteration 수 계산은
  일치하지만, 9차가 실제로 어떤 파라미터로 돌았는지까지는 재확인하지
  않았다. 9차 문서에도 이 시나리오의 정확한 실행 파라미터가 명시돼
  있지 않다.
- **`AUCTION_IDS` 요구사항이 런북(§2.2)에 문서화돼 있지 않다** —
  `#390`으로 도입된 선택 구독 요구사항 때문에 `hot-auction-pattern.js`가
  이제 정확히 200개의 서로 다른 진행중 경매 ID를 요구하는데, 런북
  커맨드는 이 환경변수 없이 적혀 있다. 이번엔 시드된 300개 중
  200개(`3001001`~`3001200`)를 수동 지정해 우회했다 — 런북에
  `AUCTION_IDS` 사용법을 추가하는 걸 권한다.
- **§4의 503/처리지연 발견은 SSE 병합과 독립적이지만, §5.1의 스왑
  급증과의 인과관계는 확정하지 못했다** — 시점이 겹치는 것만
  확인했고, 프로젝션 백로그로 인한 Redis `auction:bid:idempotency:*`
  키 폭증(세션 중 17,101→68,022, §Redis 원본 데이터 아래)이나
  재조회 증가가 메모리 압박을 키웠을 가능성이 있는 정도의 추정이다.
- **DB 직접 조회로 `performance_schema.data_lock_waits` 폴링을
  못 했다** — `dbidding` 유저에 해당 테이블 SELECT 권한이 없어서
  (`ERROR 1142: SELECT command denied ... for table
  'data_lock_waits'`) 포기했다. 대신 §3 표의 `mysql_row_lock_waits_delta`
  (Prometheus mysql-exporter 기준, 전 구간 0에 가까움)로 대체
  확인했다 — 9차의 "락 경합 없음" 결론과 일치.
- **스테이지 경계는 실측 로그 오프셋 기반이지만 여전히 근사치다** —
  각 실행의 "메인 구간이 실제로 시작한 시각"을 로그에서 1개 표본만
  확인해 오프셋으로 썼다(§3 서두). 9차보다 근거가 명확하지만 완전한
  정밀 경계는 아니다.
- **로컬 대조실험은 이번에도 하지 않았다**(prod에서만 측정).
- §4.6에서 권고한 프로젝션 컨슈머 병목 해소는 이 문서 범위 밖 —
  별도 이슈로 분리해 추적할 것을 권한다.
