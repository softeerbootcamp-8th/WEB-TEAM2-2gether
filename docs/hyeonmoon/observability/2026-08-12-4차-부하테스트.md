# 4차 부하테스트 — 3대 병목 관점 진단과 개선 방향

**대상 환경:** prod(`api.dbidding.shop`, t4g.micro, vCPU 2개, RAM 903MB) + 로컬
대조실험(Apple Silicon, 11코어/18GB, 로컬 MySQL 8.4 컨테이너, 동일 schema/시드).

**작성일:** 2026-08-11~12 (PR #377 dev→main 배포 직후 prod 재측정 → 인프라가
증폭시키는 부분과 코드/구조 자체 문제를 분리하기 위해 로컬 대조실험 추가)

**핵심 질문:** 오늘 관측된 문제를 세 축으로 나눠서, 각 축이 **① 증거가
뭔지 ② 원인이 뭔지 ③ 뭘 해야 하는지**를 정리한다. 각 축의 근거는 **어젯밤
prod 실측(원본 자료, 7장)이 1차 근거**이고, 오늘 로컬 대조실험은 그 원인을
"인프라 탓인지 구조 탓인지" 분리하기 위한 **보조 검증**이다.

| 축 | 문제 | 원인 성격 | 우선순위 | 개선 방향 |
|---|---|---|---|---|
| **① SSE 동시연결** | 500~1000 연결에서 붕괴 | 브로드캐스트 fan-out/executor 포화 (독립적 축) | **후순위** | SSE 개선 작업(범위 밖, 250은 이미 안전) |
| **② 핫경매 집중** | DB 트랜잭션/락이 경매 행 단위로 쌓임 | 구조적(어떤 하드웨어에서도 재현) | **최우선** | Redis 기반 입찰/지갑 락 전환(계획대로) |
| **③ 메모리/스왑** | Full GC가 어쩌다 뜨면 20~76초씩 걸림 | 호스트 메모리 압박(스왑) — 힙 크기 자체는 아님 | **중간, 급하지 않음** | 지금은 `-Xmx384m` 유지, 근본 해소는 스펙 업그레이드 때 |

## 1. 축 ① — SSE 동시연결 (후순위)

### 증거

| tier | SSE 연결성공(경매/알림) | http_req_failed |
|---|---:|---:|
| 250 | 100% / 100% | 5.32% |
| 500 | 100% / 71.4% | 15.54% |
| 1000 | 31.8% / 25.3% | 63.25% |

nginx 설정: `location /`(일반 API, bid-context/목록/상세/입찰 전부 포함) 타임아웃
60초, `location /api/sse/`(SSE 전용)만 1시간. 500~1000에서 브로드캐스트
executor가 포화되면 SSE 하트비트도 밀려서 60초 컷에 걸리고 대량 재접속
루프가 발생하는 구조(이전 문서에서 이미 확인, 오늘도 동일 패턴 재확인).

### 판단

**250 연결은 안전, 그 이상은 브로드캐스트 fan-out 비용 문제로 축 ②·③과
무관한 독립적인 병목.** 오늘 조사 범위에서 코드를 안 건드렸고, 별도
"SSE 쪽 개선" 작업으로 넘긴다. 우선순위를 낮게 잡은 이유는 250 연결
안에서는 이미 문제가 없고, 축 ②·③이 훨씬 더 넓은 트래픽(모든 입찰 요청)에
영향을 주기 때문이다.

## 2. 축 ② — 핫경매 집중: DB 트랜잭션/락이 쌓인다 (최우선)

### 2.1 증거 — prod

`bid-only-load.js`로 경매 1개(`3001001`)에 조회·입찰을 몰아서 실행:

```
http_req_failed: 15.91% (9,388/58,995)
읽기/쓰기 골고루 다 나쁨(bidContextReads 16.4%, bidWrites 15.6%, generalReads 16.1%)
POST 입찰(201)만 떼면 med=53ms — 성공한 입찰 자체는 빠름
```

같은 구간 nginx 응답 코드: `504`(Gateway Timeout) 4,069건, `502` 352건 —
**앱 로그의 진짜 5xx 예외는 0건.** 즉 "실패"의 실체는 앱이 60초 안에 못
끝내서 nginx가 대신 끊은 것이다(`proxy_read_timeout 60s`, 축 ③의 Full GC와
겹쳐서 더 나빠짐).

**QPS 단계별로 쪼개보면(Prometheus `http_server_requests_seconds`를 각
2분 구간별로 range query, 앱 자신이 기록한 서버측 수치):**

| QPS | 앱 요청수(2분간) | 앱 5xx | p95(서버측) | CPU 평균 | 이 구간 Full GC | HikariCP active/pending |
|---:|---:|---:|---:|---:|---:|---:|
| 50 | 7,238 | 0 | 431ms | 14.5% | - | 0.9 / 0 |
| 100 | 9,735 | 0 | 75ms | 18.0% | - | 4.6 / 0 |
| **150** | 11,662 | 0 | 759ms | 23.5% | - | **29.9 / 20.1** |
| 200 | 8,007 | 0 | 1,477ms | 18.5% | - | 29.9 / 18.9 |
| 300 | 11,837 | 0 | 890ms | 22.7% | - | 30.0 / 20.0 |
| **400** | 5,168 | 0 | 1,993ms | 21.3% | **22.4초** | 30.0 / 19.3 |

**여기가 축②·③이 겹치는 지점을 제일 잘 보여준다 — HikariCP pending은
QPS 150부터 이미 20 안팎으로 꽉 차 있다(축②, 순수 락 경합).** CPU는
14~23%로 계속 여유로운데도(=CPU가 원인이 아님, 6장 옛 결론과 일치)
pending이 일찍부터 포화된 것 자체가 축②의 증거다. **Full GC는 맨 마지막
QPS 400 구간에만 한 번 얹혔다(축③)** — 즉 이 시나리오의 기본 병목은
축②이고, 축③은 우연히 끝에 한 번 겹쳐서 상황을 더 나쁘게 만든 불운이다.

### 2.2 증거 — 로컬 (인프라 변수를 제거한 순수 구조 문제 확인)

로컬(CPU/메모리 여유 충분, Full GC 0회 조건)에서 **prod와 동일한 Hikari
max=30·Tomcat max=50** 설정으로 같은 시나리오 재현:

| QPS | Hikari active(avg/max) | Hikari pending(avg/max) | Tomcat busy(avg/max) | CPU avg | avg latency |
|---:|---:|---:|---:|---:|---:|
| 50 | 2.2 / 20 | 0.0 / 0 | 2.2 / 20 | 4.1% | 32.4ms |
| 100 | 8.1 / 30 | 3.3 / 21 | 11.4 / 50 | 4.8% | 127.1ms |
| **150** | **30.0 / 30** | **20.0 / 21** | **50.0 / 50** | 6.0% | **508.3ms** |
| 200 | 30.0 / 30 | 19.9 / 21 | 50.0 / 50 | 6.2% | 501.8ms |
| 300 | 30.0 / 30 | 19.9 / 21 | 50.0 / 50 | 6.2% | 494.5ms |
| 400 | 30.0 / 30 | 19.9 / 21 | 50.0 / 50 | 6.4% | 494.6ms |

**CPU는 끝까지 6~10%로 완전히 여유 있는데, QPS 150부터 Hikari·Tomcat 둘 다
설정 최대치로 완전히 꽉 찬다.** 실패율은 0%(로컬은 Full GC가 없으니
타임아웃도 안 남) — 즉 **이 병목은 CPU도, GC도 아니고 순수하게 "경매 행
하나를 두고 트랜잭션이 락을 기다리며 쌓이는" 구조적 한계**다. prod에서
관측된 실패는 이 구조적 한계 위에 축 ③(Full GC)이 얹혀서 증폭된 것이다.

### 2.3 풀 크기를 키워도 해결 안 됨(오히려 악화)

같은 시나리오를 Hikari/Tomcat 100/100으로 키워서 재실행:

| QPS | active(avg/max) | pending(avg/max) | busy(avg/max) | avg latency |
|---:|---:|---:|---:|---:|
| 50 | 2.3/20 | 0.0/0 | 2.5/20 | 33.8ms |
| **100** | 35.7/100 | 0.1/2 | 35.8/100 | 413.0ms |
| **150** | **99.9/100** | 0.1/1 | **100.0/100** | **988.4ms** |
| 200 | 99.9/100 | 0.1/1 | 100.0/100 | 961.6ms |
| 300 | 99.9/100 | 0.1/1 | 100.0/100 | 927.9ms |
| 400 | 99.9/100 | 0.1/1 | 100.0/100 | 894.5ms |

풀을 키우니 **커넥션 대기(pending)는 거의 사라졌지만(20→0), 포화 후
평균 latency는 오히려 약 2배 나빠졌다(500ms→930ms).** 이유: 커넥션이
부족해서 미리 걸러지던 요청들이, 풀이 커지자 전부 커넥션을 받고 들어가서
**MySQL 내부 락 대기줄에 동시에 더 많이 쌓인다.** 경매 행을 한 번에 처리할
수 있는 트랜잭션은 여전히 1개뿐이므로 처리 속도(처리량)는 그대로고, 대기줄만
깊어져 개별 요청은 더 느려진다. **풀 크기 튜닝으로 해결되는 문제가 아니다.**

Tomcat 스레드가 Hikari보다 많이 설정돼 있으면(30 vs 50), Hikari가 먼저
꽉 찬 뒤 나머지 스레드도 "Hikari 커넥션 대기"로 블록되면서 따라서 꽉
찬다(active=30/30과 busy=50/50이 동시에 천장을 찍는 패턴으로 확인됨) —
Tomcat 스레드 수를 늘리는 것도 마찬가지로 실제 처리량엔 도움이 안 된다.

### 2.4 wallet_holds 데드락 (같은 구조적 문제의 또 다른 증상)

오늘 배포 후 2시간 동안 36건 발생. 실제 InnoDB 데드락 그래프(`SHOW ENGINE
INNODB STATUS`, DB 서버에 직접 접속해 확보):

```
TX1: lockWallet(user_id=910491) 대기 중, wallet_holds 행 하나 이미 잠금 보유
TX2: sumHeldAmountForUpdate(wallet_id=523) 실행 중, wallets 행 이미 잠금 보유,
     TX1이 든 wallet_holds 행 기다리다 데드락 → TX2 롤백
```

`DbBidExecutor.shouldReleasePreviousHoldFirst()`(작은 userId 먼저 잠그는
순서 규칙)는 **한 트랜잭션 안에서 지갑 2개 사이의 순서만 보장**한다. 한
유저가 서로 다른 독립 거래(다른 경매, 다른 상대)에 동시에 낀 3개 이상
지갑이 얽히면 이 페어와이즈 규칙으로 못 막는 사이클이 생긴다 — 오늘
InnoDB가 잡아낸 그림이 정확히 이 패턴이다. `EXPLAIN`으로 확인한 결과
인덱스 문제는 아니다(`idx_wallet_holds_wallet_status`, `ref` 타입,
`filtered=100%` 정확히 사용).

### 2.5 개선 방향

**계획대로 Redis 기반 입찰/지갑 락 전환이 정답 방향이다** — 지금 병목의
본질(경매 행 단위 직렬화, wallet_holds 잠금 자원 분리로 인한 데드락 가능성)을
정확히 겨냥한다. 재검증 기준을 지금 잡아두자:

> **핫경매 집중 시나리오(`bid-only-load.js` HOT_AUCTION_ID, pool은 prod
> 현재값 30/50 고정)에서 QPS 300~400까지도 Hikari active/pending이 완전
> 포화되지 않아야 한다.** 지금은 QPS150부터 30/30·pending 20으로 완전
> 포화됨 — Redis 전환 후 이 숫자 자체가 안 뜨는 게 성공 기준.

풀 크기 튜닝(2.3절 결론)은 **지금(DB 행 락 기반) 아키텍처에 한정된
결론**이다. Redis Lua 기반으로 바뀌면 락의 성격 자체가 달라지므로, 전환
후에는 풀 크기 튜닝을 다시 검토해야 한다(전제가 바뀌므로 결론을 그대로
이어가면 안 됨).

## 3. 축 ③ — 메모리/스왑: Full GC가 뜨면 크게 터진다 (급하지 않음)

### 3.1 증거 — prod

오늘 배포 후 실행한 5개 시나리오 전체에서 Full GC(`G1 Old Generation`,
cause `G1 Compaction Pause`) **18회, 총 605초.** 시나리오별 누적 추이
(Prometheus `jvm_gc_pause_seconds_count/sum`을 매 시나리오 종료 직후 조회):

| 시점 | 누적 발생 횟수 | 누적 pause(초) | 이 구간 신규 발생 |
|---|---:|---:|---|
| 250(1차) 종료 후 | 2 | 152.5 | 2회, **평균 76초/회** |
| 250(재실행) 종료 후 | 3 | 177.8 | 1회(25.4초) |
| 500 종료 후 | 8 | 277.1 | 5회(99.3초) |
| 1000 종료 후 | 16 | 565.1 | 8회(288.0초) |
| hot-auction-pattern 종료 후 | 16 | 565.1 | **0회** |
| bid-only-load 분산 종료 후 | 16 | 565.1 | **0회** |
| bid-only-load 핫경매집중 종료 후 | 18 | 605.0 | 2회(39.9초) |

**Full GC가 뜬 시나리오(250/500/1000/핫경매집중)와 안 뜬 시나리오
(hot-auction-pattern, bid-only-load 분산)가 정확히 4장의 "결과 갈림"과
일치한다.** 발생 시점도 QPS와 뚜렷한 상관관계가 없다 — 500-tier는 QPS
50(제일 낮은 구간)에서도 떴다(7.2절 참고).

```
전체 시스템 메모리(idle 시점에도): 776~831Mi/903Mi 사용, swap 1.0~1.2GB 사용 중
```

### 3.2 로컬 대조실험 — 힙 크기 단독으로는 재현 안 됨

| 조건 | Full GC | 비고 |
|---|---:|---|
| 로컬, Xmx=4g | 0회 | 여유 있게 넉넉히 준 경우 |
| 로컬, Xmx=384m(prod와 동일) | **0회** | 메모리 압박 없는 상태에서는 384MB로도 충분 |
| 로컬, Xmx=200m | **85회, 총 4.4초(평균 52ms/회)** | 힙을 확 줄이면 뜨긴 하지만 무해함 |

**200MB로 낮추면 Full GC가 자주 뜨긴 하는데, 압축 자체가 빨라서(RAM 직접
접근) 1회당 52ms — 아무 영향 없다.** prod는 정반대로, **딱 2번 떴는데
한 번에 20~76초**였다. 이 차이가 핵심이다.

### 3.3 진짜 원인 — 힙 크기가 아니라 스왑

Full GC가 힙을 압축하려는데 **그 페이지 일부가 스왑(디스크)에 나가 있으면,
압축 한 번 할 때마다 디스크 I/O 왕복이 끼어든다.** 로컬(스왑 없음)에서
같은 양의 GC 작업이 52ms인데, prod(스왑 상시 사용)에서는 같은 작업이
수백~수천 배 느려진다. **즉 "힙이 작다"가 원인이 아니라 "호스트 전체
메모리가 이미 빡빡해서 스왑을 쓰고 있고, 그 상태에서 GC가 걸리면 스왑된
페이지를 건드릴 확률이 생긴다"는 게 진짜 메커니즘이다.**

### 3.4 그래서 `-Xmx`를 어떻게 잡아야 하나

- **더 낮추면 안 된다** — 200MB 테스트처럼 Full GC 빈도가 늘어나고, 그만큼
  "스왑된 페이지를 건드릴 기회"도 늘어난다(로컬처럼 무해하게 넘어간다는
  보장이 prod 조건에서는 없다).
- **더 올리는 것도 검증되지 않았다** — 지금 이미 스왑을 쓰고 있는
  903MB 호스트에서 힙을 더 키우면 OS/캐시 쪽 여유를 깎아 스왑을 오히려
  악화시킬 수 있다. 로컬 4GB 테스트는 "코드 자체엔 문제가 없다"는 것만
  증명했지, "prod에서 더 올려도 되는지"는 증명하지 못한다.
- **결론: 지금은 `-Xmx384m` 유지가 맞다.** 위/아래로 바꿀 확실한 근거가
  없고, 근본 해결(스왑 자체를 없애는 것)은 호스트 총 메모리 문제라
  **스펙 업그레이드 시점으로 넘긴다.** 그 전까지는 "가끔 아주 크게
  터지는" 리스크를 안고 가는 것이고, 이건 코드/설정으로 지금 당장
  없앨 수 있는 종류의 문제가 아니다.

## 4. 세 축이 서로 어떻게 겹치는지

오늘 prod에서 나쁘게 나온 시나리오(250-tier, 500-tier, 1000-tier, 핫경매
집중)는 전부 **축 ②(DB 락) 또는 축 ③(Full GC) 중 하나 이상이 낀 경우였고**,
반대로 깨끗하게 나온 시나리오(hot-auction-pattern 250, bid-only-load
분산)는 **둘 다 안 낀 경우였다.** 즉 오늘 관측된 "나쁜 결과"들은 새로운
제3의 원인이 아니라, 이 두 가지가 다른 강도로 겹쳐서 나타난 것으로 정리된다.

| 시나리오 | 축② 락 경합 | 축③ Full GC | 결과 |
|---|:---:|:---:|---|
| pure-throughput 250(재실행) | 약함(분산) | 있음(1회) | 실패 5.3% |
| pure-throughput 500/1000 | 약함(분산) | 있음(5~8회) | 실패 15.5~63.3% |
| hot-auction-pattern(250) | 있음(3개 핫경매) | **없음** | 실패 0.016% |
| bid-only-load 분산 | 없음 | **없음** | 실패 0.0007% |
| bid-only-load 핫경매집중 | **강함(1개 집중)** | 있음(2회) | 실패 15.9% |

## 5. 결론

1. **핫경매 집중(축②)이 제일 급하고, 계획된 Redis 전환이 정답이다.**
   CPU 여유 있는 상태에서도 재현되는 순수 구조적 문제로 확정됐다(2.2절).
   풀 크기 튜닝으로는 해결 안 되고 오히려 역효과다(2.3절).
2. **메모리/스왑(축③)은 코드로 지금 당장 고칠 수 없다.** `-Xmx384m`을
   유지하되, 근본 해소는 스펙 업그레이드 시점으로 넘긴다(3.4절). 그
   전까지는 "가끔 크게 터지는" 리스크를 인지하고 가는 것이다.
3. **SSE(축①)는 후순위가 맞다.** 250 연결까지는 이미 안전하고, 축②·③과
   독립적인 문제라 순서를 늦춰도 다른 개선 작업에 지장이 없다.
4. **다음 baseline(재검증 시나리오) 제안:**
   - Redis 전환 검증: `bid-only-load.js` HOT_AUCTION_ID, pool 30/50 고정,
     QPS 300~400에서 Hikari 포화 안 되는지 확인 (2.5절 기준)
   - SSE 개선 검증: `pure-throughput.js` 250/500/1000, 1000에서도 SSE
     연결성공률 ≥99% 확인
   - 리그레션 체크: `bid-only-load.js` 분산 + pure-throughput, 계속
     0%대 유지되는지 확인
   - 세 시나리오 모두 `-Xmx384m` 고정 상태로 비교해야 전후 비교가
     인프라 변수에 흔들리지 않는다.

## 6. 한계 및 주의사항

- 로컬 대조실험은 macOS라 리눅스 cgroup 같은 정교한 CPU/메모리 제한을
  못 걸어서, "prod와 완전히 동일한 조건"이 아니라 "인프라 변수(CPU 파워,
  메모리 압박)를 제거했을 때 코드/구조 자체의 동작"을 보는 용도로만
  썼다. 정량적 숫자(latency 절댓값)를 prod와 1:1로 비교하면 안 되고,
  **패턴(포화 여부, GC 발생 여부)만 비교 대상**이다.
- 3.2절의 200MB 테스트는 이번 특정 부하 패턴(분산 300~400 QPS)에서의
  결과다. 다른 트래픽 패턴(예: 핫경매 집중)에서 힙-스왑 상호작용이
  다르게 나타날 수 있어 일반화하면 안 된다.
- wallet 데드락(2.4절)의 InnoDB 스냅샷은 36건 중 1건만 상세 분석했다 —
  나머지가 전부 같은 메커니즘인지는 확인 안 됐다(로그의 쿼리 패턴은
  동일했다).
- SSE(축①)는 이번 조사에서 코드/설정을 전혀 안 건드렸다 — 오늘 데이터는
  "현황 재확인" 수준이고, 별도 개선 작업의 입력값으로만 쓰인다.

## 7. 부록 — prod QPS 단계별 상세 원본 (어젯밤 실측)

축②·③ 요약에 다 못 넣은 나머지 시나리오의 QPS 단계별 분해다. 전부
Prometheus `http_server_requests_seconds`/`hikaricp_connections_*`/
`jvm_gc_pause_seconds_*`를 각 시나리오의 실제 시작 시각 기준 2분 구간별로
range query 해서 뽑았다(k6 결과 JSON은 집계값만 있어서, 서버가 직접 기록한
값을 따로 조회함).

### 7.1 pure-throughput 250(재실행)

| QPS | 앱 요청수(2분간) | 앱 5xx | p95(서버측) | CPU 평균 | 이 구간 Full GC | HikariCP active/pending |
|---:|---:|---:|---:|---:|---:|---:|
| 50 | 7,465 | 0 | 352ms | 28.6% | - | 0.4 / 0 |
| 100 | 10,050 | 0 | 21ms | 28.3% | - | 1.1 / 0 |
| 150 | 17,087 | 2 | 315ms | 53.2% | - | 13.9 / 7.8 |
| 200 | 16,337 | 1 | 872ms | 51.7% | - | 17.9 / 6.4 |
| **300** | 7,853 | 0 | 1,223ms | 56.7% | **29.0초** | 26.2 / 14.8 |
| 400 | 28,394 | 0 | 389ms | 62.2% | - | 29.3 / 18.6 |

QPS 300 구간에서 Full GC 29초가 떴고, 그 여파로 요청 처리량 자체가 뚝
떨어졌다(7,853건 — 앞뒤 구간의 절반 이하). QPS 400 구간은 오히려
깨끗하다(28,394건) — GC로 쌓였던 큐가 풀리고 나서 회복된 것으로 보인다.

| QPS | 앱 요청수 | 앱 5xx | p95 | CPU | Full GC | HikariCP active/pending |
|---:|---:|---:|---:|---:|---:|---:|
| **50** | 7,831 | 0 | 638ms | 34.1% | **24.1초** | 10.5 / 6.2 |

500-tier는 6단계 중 3단계(50/200/400)에서 Full GC를 맞았다 — 시작하자마자

1000-tier는 6단계 중 3단계(50/150/200)에서 Full GC를 맞았고, 요청량

### 7.5 nginx 응답 코드 전체 분포 (bid-only-load 핫경매집중 구간, 14:45~14:58 UTC)

| 코드 | 건수 | 의미 |

| 200 | 43,455 | 정상 |
| 400 | 5,795 | 정책적 거부(가격 등) |
| 499 | 5,475 | 클라이언트(k6) 연결 끊음 — 자체 타임아웃으로 포기 |
| **504** | **4,069** | Gateway Timeout — 앱이 60초 안에 응답 못함 |

| 401 | 204 | 인증 실패 |

앱이 실제로 던진 에러가 아니다.
