## 정량 데이터 — 구간(스테이지)별 세부

위 종합표는 실행 전체 평균/누적치라 **어느 QPS 구간에서 무너졌는지**가 안 보인다.
아래는 각 실행의 **로컬 k6 콘솔 로그**(`/tmp/k6-round5-*.log`, 1초 간격
`running (MM:SS.s), N complete and M interrupted iterations` 라인)를 직접 파싱해
`pure-throughput`/`bid-only-load`의 6단계 QPS 계단(스크립트 설정: `mainStartTime` 이후
2분씩 50→100→150→200→300→400)과 `hot-auction-pattern`의 5분 정속 구간(1분 단위)별
**완료/중단 iteration 수**를 그대로 뽑은 것이다.

**한계(먼저 밝힘):** 이 구간별 수치는 **iteration 완료/중단 수**만 담고 있다.
k6가 이번엔 커스텀 요약본만 저장했고(`--out json` 원시 타임스탬프 덤프는
안 켬) 그래서 구간별 latency/에러율까지 쪼개려면 Prometheus 히스토리
range query에 의존해야 한다.

**정정(6차 문서 작성 중 확인함):** 처음엔 "모니터링 서버 Prometheus의
TSDB 보존 구간이 `2026-08-13T00:00:00Z`부터로 말려서 이번 테스트 구간이
유실됐다"고 판단했는데, 이건 `/api/v1/status/tsdb`의 `headStats.minTime`만
보고 내린 잘못된 결론이었다 — 그건 in-memory head 블록 지표일 뿐이고,
디스크에 이미 컴팩션된 과거 블록은 별개로 여전히 쿼리 가능하다. 실제로
6차 문서 작성 중 이 구간(12:33~16:33 UTC)에 직접 range query를 날려보니
정상적으로 데이터가 나왔다(hikari/CPU/GC/스왑 등, 8-round6 문서 §7 참고).
즉 **이번 문서의 구간별 표에 latency/에러율이 빠진 건 데이터가 없어서가
아니라 시간이 부족해 처리하지 않아서다** — 이후 필요하면 재조회해서
채울 수 있다.
(`interrupted`는 k6가 VU 풀 부족/graceful stop 때문에 iteration을 강제 종료한
건수라 http 400/409/5xx 응답과는 다른 지표다 — 모든 구간에서 0으로 나온 건
정책 거부·서버에러가 나도 iteration 자체는 끝까지 실행됐다는 뜻이고, 실제
중단은 전부 마지막 drain 구간에 몰려 있었다.)

### OOM과 스테이지 대조 (1차/3차)

| 구분 | k6 실행 시작(UTC) | 실제 OOM 시각 | 시작 대비 경과 | 대응 스테이지 |

| 3차 | 2026-08-12 14:25:32 | 2026-08-12 14:31:42.678(힙덤프 타임스탬프, KST 23:31:42.678) | 약 370초 | QPS150 구간(275~395s) 안, QPS200 진입 95초 전 |

(정정: 초안에서 3차 시작을 2차 시작 시각(13:48:00 UTC)으로 잘못 잡아
"테스트 종료 30분 뒤"라고 썼었다 — 실제 3차 실행 시작은 14:25:32 UTC이고
그 기준으로 다시 계산하면 위 표대로 QPS150 구간 안이다.)

**두 실행 다 QPS 계단이 한창 진행 중일 때 터졌다** — 즉 OOM은 "테스트가
끝난 뒤 뒤늦게" 온 게 아니라 **부하 자체가 걸려 있는 동안** 터졌다. 이건
3.3절 근본원인과 그대로 이어진다: 범인은 `UrgentNotificationRecoveryScheduler`
(90초 주기, ENDING 경매 전용)가 아니라 **`NonUrgentNotificationRecoveryScheduler`
(300초 주기)의 `recoverOpenOutbidNotifications`다.** 이번 부하테스트가 쓰는
300개 시드 경매는 전부 `status='OPEN'`, `close_time=NOW()+7일`이라
테스트 도중 `ENDING`으로 전이되는 경매가 없다 — 그래서 Urgent 쪽 후보는
거의 항상 0건이고, 부하 도중 300초마다 한 번씩 OPEN 경매 300개 전체를
훑는 NonUrgent 쪽만 후보가 쌓인다. 부하가 QPS150~QPS400까지 올라가는
6~13분 사이에 이 300초 주기 스캔이 최소 1~2번은 걸렸을 시점(370초,
661초 둘 다 300초 배수 근방)과 실제 OOM 시각이 겹치는 게 우연이 아닐
가능성이 높다. 다만 이 두 스케줄러는 코드상 실행 시작을 로그로 남기지
않아서(예외 발생 시에만 `log.error`) **"몇 시 몇 분 몇 초에 정확히 그
스케줄러 실행이 터뜨렸다"는 초 단위 로그 한 줄은 없다** — 위 시각 대조가
현재 갖고 있는 가장 근접한 증거이지 확정 증거는 아니다.

### 1.2 브로드캐스트 포화 — 4차와 가장 크게 달라진 지표

```

dbidding_sse_broadcast_saturated_total{executor="notification-fanout"}: 0.0
dbidding_sse_broadcast_saturated_total{executor="wallet"}: 0.0
```

**250/500 tier 전 구간에서 포화 0건.** 어젯밤(4차) 250-tier에서도 이미 0이긴
했지만, **500-tier에서 SSE 연결성공률이 71.4%(알림)→100%로 확실히 개선된 게
선택 구독 효과로 보인다** — `?auctionIds=...`로 화면이 보는 경매만 구독하니,
한 번의 입찰 이벤트가 브로드캐스트해야 할 대상(구독자 수)이 "전체 연결
수"가 아니라 "그 경매를 보고 있는 사람 수"로 줄어든 것이 직접 원인이다.

### 1.3 1000-tier — 여전히 위험권, 이번엔 다른 이유로

1000-tier는 여전히 붕괴하지만, **원인이 브로드캐스트 포화(4차까지의 원인)가
아니라 힙 OOM으로 바뀌었다.** 브로드캐스트 포화 카운터는 1000-tier에서도
0을 유지했다(3차 시도 기준). 즉 SSE 자체의 fan-out 병목은 해소됐고, 그
자리를 축③(메모리)이 대신 차지했다.

### 1.4 판단

**SSE 선택 구독은 의도한 효과를 냈다.** 250/500 tier에서 브로드캐스트가
더 이상 병목이 아니다. 1000-tier가 여전히 위험한 건 SSE 설계 문제가 아니라
별개의 메모리 문제(5장)로 성격이 바뀌었다.

## 3. 축③ — 실제 heap OOM 발견 (신규, 가장 중요한 발견)

### 3.1 증거

1000-tier 테스트 도중 세 번에 걸쳐 다른 정도로 재현:

| 시도 | 실패율 | 실제 OOM(진짜 예외, 시작배너 오탐 제외) | 관리포트(9091) | 힙덤프 |
|---|---:|---:|---|---|
| 1차 | 82.68% | 71건(추정, 이후 로그 회전으로 정확한 수 재확인은 못 함) | 사망(9091-Poller 스레드 OOM으로 죽음) | 없음(옵션 미적용) |
| 2차 | 30.90% | 0건(재현 안 됨) | 정상 | 없음 |
| 3차 | 98.38% | **106건** | 사망 | **535MB 확보(`heapdump.hprof`)** |

첫 시도에서 `Exception in thread "http-nio-9091-Poller" java.lang.OutOfMemoryError: Java heap space`,
`Exception in thread "HikariPool-1:connection-closer" java.lang.OutOfMemoryError: Java heap space`
확인. 관리포트 담당 스레드가 죽어서 컨테이너 재시작 전까지 `/actuator/*`가
영구적으로 응답 불가 상태가 됐다(메인 API 8080은 일부 계속 응답).

**부수 발견:** 첫 OOM 이후 로그에 반복적으로 찍히는 에러 수십 건 중
다수는 진짜 새 OOM이 아니라 **연쇄 효과**였다 — Slack 알림용 내부
`HttpClient`의 selector 스레드도 같은 시점에 죽어서, 그 뒤 발생하는
WARN/ERROR 로그마다 Slack 알림을 보내려다 "selector manager closed"로
실패 → 그 실패도 로그로 남아 또 Slack 시도 → 반복되는 패턴이었다.

### 3.2 힙덤프 분석 — 정확히 뭘 알 수 있고 뭘 모르는지

535MB 힙덤프를 직접 파싱(HPROF 바이너리 포맷, MAT/jhat 등 도구 없이 커스텀
파서 작성)해서 클래스별 히스토그램을 뽑았다. 상위 항목(shallow bytes 기준):

| 클래스 | 인스턴스 수 | 총 shallow bytes |
|---|---:|---:|
| byte[] | 947,706 | 157.4MB |
| char[] | 7,349 | 55.1MB |
| object[] | 428,978 | 49.6MB |
| com/mysql/cj/NativeQueryBindValue | 60,077 | 6.1MB |
| org/antlr/v4/runtime/atn/ATNConfig | 184,923 | 5.9MB |
| **com/dbidding/auction/domain/Bid** | **60,072** | 3.8MB |
| **org/hibernate/engine/internal/EntityEntryImpl** | **47,267** | 3.6MB |
| com/mysql/cj/protocol/a/NumberValueEncoder | 60,072 | 3.4MB |
| **org/hibernate/engine/internal/StatefulPersistenceContext$EntityHolderImpl** | **47,269** | 3.0MB |
| **com/dbidding/notification/Notification** | **47,268** | 2.7MB |
| org/hibernate/query/sqm/tree/expression/SqmNamedParameter | 60,144 | 2.0MB |
| com/mysql/cj/protocol/a/result/ByteArrayRow | 60,072 | 2.0MB |
| (그 외 60k대 카운트인 Hibernate SQM/JDBC 바인딩 메타데이터 다수) | ~60k씩 | ~4MB |

**총합(파서 검증용):** 전체 9,637개 클래스/배열 타입 shallow bytes 합계는
**359.1MB**(전체 인스턴스 5,212,783개) — 이게 hprof 파일 크기(535MB, 포맷
오버헤드 포함)보다 작고 `-Xmx384m`보다 작아서 정합성은 맞는다.

**중요한 재검토 — "60k/47k건이 곧 OOM 원인"은 과장이었다.** `Bid`/`Notification`/
`EntityEntryImpl`/`EntityHolderImpl`/`NativeQueryBindValue`/`ByteArrayRow`/
`NumberValueEncoder`/SQM 파라미터 메타데이터까지, **카운트가 정확히
47k~60k대로 일치하는 클래스를 전부** 더해도 **약 33MB**밖에 안 된다.
384MB 힙을 이것만으로 채울 수 없다. **진짜 큰 덩어리는 `byte[]`(157.4MB) +
`char[]`(55.1MB) + `object[]`(49.6MB) = 262MB, 전체의 73%다.**

이 세 타입은 **shallow-size 히스토그램만으로는 "누가 참조하고 있는지"
알 수 없다** — 어떤 코드가 이 배열들을 물고 있는지 알려면 retained-size/
dominator-tree 분석(MAT 등 전용 도구)이 필요한데 이번엔 없었다(§6 한계).
`char[]`가 인스턴스당 평균 7.5KB(7,349개인데 55.1MB)로 비정상적으로 큰 건
눈에 띄지만, 이게 알림 복구 배치의 문자열인지, 3.1절에서 언급한 Slack
알림 실패 연쇄 로그(스택트레이스 포함 긴 메시지)인지, 아니면 전혀 다른
경로(SSE payload 직렬화, MySQL 드라이버 응답 버퍼 등)인지 **이 데이터만으론
확정할 수 없다.**

**그래서 결론을 이렇게 바꾼다:** `recoverOutbidNotificationsForCandidates()`가
페이지네이션 없이 6만 건을 한 번에 로드하는 건 **코드로 확인된 실제 버그이자
비정상 패턴**이고(평소엔 이 정도 규모의 후보가 쌓일 일이 없다 — 3.4절),
힙덤프에도 정확히 그 카운트(47k~60k)로 흔적이 남아 **이 코드가 그 시점에
실행 중이었다는 증거**는 확실하다. 하지만 이 배치 자체가 차지하는 크기는
33MB 정도라 **"이것 하나가 OOM의 유일한 원인"이라고 하기엔 근거가
부족하다** — 정확한 표현은 "이미 359MB(거의 384MB 한계)까지 찬 힙 위에
이 배치가 마지막 30여MB를 더 얹은, **확인 가능한 기여 요인 중 하나**"다.
나머지 262MB(byte[]/char[]/object[])의 진짜 주인은 이번 분석 도구의
한계로 특정하지 못했다 — MAT 등으로 재분석하면 더 정확히 나눌 수 있다.

### 3.3 코드 원인 (확인함)

```java
// NotificationReconciliationService.recoverOutbidNotificationsForCandidates()
List<Bid> outbidCandidates = bidRepository.findLatestBidPerBidderByAuctionIdIn(candidateAuctionIds).stream()
        .filter(bid -> bid.getStatus() == BidStatus.OUTBID)
        .toList();
...
for (Bid latestBid : outbidCandidates) {
    ...
    saveIgnoringDuplicate(() -> notificationService.saveForBid(...));  // 페이지네이션/청크 없이 루프
}
```

`UrgentNotificationRecoveryScheduler`(90초 주기, `recoverEndingOutbidNotifications`
→ `auctions.status = ENDING`인 경매만 후보)와 `NonUrgentNotificationRecoveryScheduler`
(300초 주기, `recoverOpenOutbidNotifications` → `bids.status = LEADING`이고
`auctions.status = OPEN`인 경매 전부가 후보)가 둘 다 이 메서드를 호출하는데,
**실제 이번 OOM의 범인은 후자다.** k6 부하테스트 시드 SQL
(`009-k6-load-test-auctions.sql`)이 300개 경매를 전부 `status='OPEN'`,
`close_time=NOW()+7일`로 깔아두기 때문에 — 즉시낙찰가도 없어서 — 테스트
도중 이 300개 경매 중 어느 하나도 `ENDING`으로 전이되지 않는다. 그래서
`UrgentNotificationRecoveryScheduler`(ENDING 전용)는 이 테스트 내내 후보가
사실상 0건이고, **입찰이 몰릴 때마다 실제로 후보가 쌓이는 쪽은
`NonUrgentNotificationRecoveryScheduler`의 OPEN 경로뿐이다.**

**"6만 건이 어떻게 쌓였나"— 핵심은 이 메서드의 메인 쿼리에 시간 윈도우가
아예 없다는 것이다.** `recoverOutbidNotificationsForCandidates(candidateAuctionIds,
windowStart)`에서 `windowStart`는 "최근 종료된 경매"를 후보에 추가할 때만
쓰이고, 정작 `bidRepository.findLatestBidPerBidderByAuctionIdIn(candidateAuctionIds)`
호출에는 어떤 시간 조건도 없다 — **이 candidateAuctionIds(=현재 OPEN인 경매들)에
대해 그 경매가 생성된 이래 지금까지 입찰한 모든 (입찰자, 경매) 조합의 "최신
입찰"을 전부 가져온다.** k6 테스트용 300개 경매(`3001001~3001300`)는 스키마가
안 바뀌는 한 재시딩되지 않고 그대로 재사용되므로, 이번 라운드 5의 8개 실행뿐
아니라 **어제(8/11)부터 이어진 이전 테스트 세션들에서 이 300개 경매에 입찰했던
모든 유저까지 누적된 채로 남아있다.** 그래서 6만 건은 "이번 300초 사이에 새로
들어온 입찰 수"가 아니라 **이 300개 경매가 지금까지 받은 입찰자 조합 전체의
스냅샷**이다 — 스케줄러가 돌 때마다(5분마다) 이미 알림 보낸 것도 포함해서
이 전체를 매번 다시 로드한 뒤에야 Java 쪽에서 `alreadyNotifiedBidIds`로
걸러낸다. 즉 문제는 "300초 동안 쌓인 양"이 아니라 **경매 하나의 전체 생애
동안 쌓인 입찰자 수가 그대로 매 사이클 재로드 대상이 된다는 것** — 시딩
경매의 `close_time`이 7일 뒤라 몇 번을 재사용해도 절대 안 닫히니, 이 값은
테스트를 반복할수록 계속 불어나기만 한다. 이 상태로 페이지네이션 없이
한 번에 다 로드하고 루프를 도니, 그 한 번의 스케줄러 호출이 6만 건 `Bid` +
4.7만 건 `Notification`을 동시에 물고 처리하게 된다.

흥미로운 점: 같은 클래스의 `insertAllIgnoringDuplicates()`(경매 생성 알림
fan-out)는 `FAN_OUT_CHUNK_SIZE = 10_000` 청크 처리가 **이미 있다.** 상회입찰
복구 경로에만 이 패턴이 빠져 있었다.

### 3.4 왜 이번에만 터졌나 (축①과의 연결)

어젯밤(4차)에도 1000-tier를 여러 번 돌렸지만 진짜 heap OOM은 없었다(Full
GC가 심하게 느려지긴 했어도). **SSE 선택 구독(#399)이 브로드캐스트
병목을 없애면서, 같은 부하에서 실제로 처리되는 요청/입찰량 자체가
늘어났다** — 3.2절 정정을 반영하면 이게 두 갈래로 힙을 밀어붙였다고 보는
게 더 정확하다: (1) 처리량이 늘어난 만큼 힙의 대부분(byte[]/char[]/
object[] 262MB)을 차지하는 일반 요청·연결 버퍼 자체도 이전보다 더 많이
쌓였을 것이고(직접 증거는 없음, 정황), (2) 상회입찰 이벤트도 더 많이
실제로 성사되면서 복구 스케줄러의 후보 수(확인된 33MB어치)도 늘었다.
**즉 SSE 개선이 문제를 만든 게 아니라, 병목 하나를 치우면서 힙 사용량을
전반적으로 밀어올렸고, 그 위에 알림 복구 배치의 무제한 로드 버그가
얹히면서 처음으로 384MB 한계를 넘겼다는 게 가장 설득력 있는 설명이다.**
다만 (1)은 정황 추정이고, 262MB의 실제 소유자는 이번 분석으로 특정하지
못했다는 점을 다시 강조한다(3.2절).

### 3.5 후속 조치

`NotificationReconciliationService.recoverOutbidNotificationsForCandidates()`에
청크 처리를 추가하는 작업을 별도로 분리해뒀다(백그라운드 작업 스폰,
`insertAllIgnoringDuplicates()`의 기존 청크 패턴을 참고해 적용 예정).

## 5. GC 타임라인 (오늘 전체)

| 구간 | 신규 Full GC | 비고 |
|---|---:|---|
| 250-tier 종료 후 | 2회, 47.9초 | |
| 500-tier 종료 후 | +7회(누적 9), 132.8초 신규 | |
| 1000-tier 1~3차 | (OOM으로 정상 GC 집계 불가/재시작 발생) | |
| 재시작 후 hot-auction+bid-only×2 | **1회, 15.4초** | 매우 낮음 |

**재시작 이후 구간이 훨씬 깨끗하다** — Full GC가 딱 1번(15.4초)뿐이었다.
이는 (a) 재시작으로 힙이 완전히 초기화됐고, (b) 뒤쪽 세 시나리오가
1000-tier급 극단적 부하는 아니었기 때문으로 보인다. 4차(어젯밤)와
비교하면 이번 5차의 GC 문제는 여전히 1000-tier에 집중돼 있고, 그 성격이
"느린 GC"에서 "진짜 OOM"으로 악화됐다는 게 핵심 차이다.

## 6. 한계 및 주의사항

- **docker 로그 회전으로 재시작 전 구간(250/500/1000×3)의 정확한
  데드락 카운트를 재확인하지 못했다.** OOM으로 인한 로그 폭증(Slack
  알림 실패 연쇄) 때문에 평소보다 로그 회전이 훨씬 빨랐던 것으로
  보인다. 축②의 "재시작 후 0건" 결론은 유효하지만, "재시작 전에도
  0건이었다"는 아니다 — 그 구간은 확인 불가로 남긴다.
- **hot-auction-pattern이 재시작 직후 첫 시나리오라 워밍업 영향이
  완전히 배제되지 않는다**(재시작 후 10분 대기는 했지만, 어젯밤
  4차의 250-tier 1차/재실행 케이스처럼 첫 부하 시나리오가 유독
  나쁘게 나오는 패턴이 이전에도 있었다).
- **힙덤프 분석은 커스텀 HPROF 파서로 직접 작성해서 진행했다**(MAT/jhat
  같은 표준 도구 미설치). 표준 도구로 재검증하면 더 정밀한 retained-size
  분석(단순 shallow size가 아니라 참조 체인 기반)이 가능하다 — 이번
  분석은 shallow size 히스토그램 수준이다. **이게 실제로 결론에 영향을
  준 지점이 있다**: 알림 복구 배치와 카운트가 일치하는 클래스들을 전부
  더해도 33MB 정도(총 힙 359MB의 9%)뿐이라, 이 배치가 "OOM의 유일한
  원인"이라고는 못 하고 "확인된 기여 요인 중 하나"로 결론을 낮췄다
  (3.2절). 힙의 73%(byte[]/char[]/object[] 262MB)를 누가 들고 있는지는
  이번 분석 방법으로는 특정 못 했다 — retained-size 분석이 이 부분을
  풀 수 있는 다음 단계다.
- **1000-tier 3차 시도(98.38% 실패)는 사실상 완전 붕괴 상태의 극단치라
  이 값 자체를 "1000-tier의 대표 실패율"로 쓰면 안 된다** — OOM이 낀
  이후의 결과라 정상적인 "SSE 500~1000 연결 붕괴" 패턴과 섞여있다.
- 이번에도 로컬 대조실험은 하지 않았다(prod에서만 재현 확인) — 로컬로
  이 정확한 알림 복구 배치 시나리오를 재현하려면 300개 경매에 극단적인
  상회입찰을 만들어내는 별도 준비가 필요하다.
- **"정량 데이터 — 구간별 세부"의 구간별 수치는 완료/중단 iteration
  수만 담고 있다, 구간별 http 실패율·latency는 없다.** ~~이유는 Prometheus
  보존기간 만료~~ **(정정) 데이터는 살아있었다** — `headStats.minTime`만
  보고 유실됐다고 잘못 판단한 거였다(위 §정량 데이터 정정 문단 참고).
  단순히 이 문서 작성 시점엔 시간 관계상 구간별 latency까지는 처리하지
  않았을 뿐이다. 8-round6 문서 작성 중 실제로 이 구간(bid-only-load
  핫경매집중 등)에 재조회해서 latency/GC/스왑 데이터를 뽑아냈다.

## 7. 결론

1. **SSE 선택 구독(#399)은 성공적이다.** 브로드캐스트 포화가 250/500/1000
   tier 전부에서 0을 유지했고, 500-tier SSE 연결성공률이 71.4%→100%로
   개선됐다.
2. **wallet_holds 락 제거(#398)도 성공적이다.** 재시작 후 구간(어젯밤
   36건 나던 것과 동일한 시나리오 포함) 데드락 0건, 핫경매 집중
   실패율도 15.91%→8.78%로 개선.
3. **하지만 이 두 개선이 새로운 문제를 드러냈다 — 힙덤프에서
   `NotificationReconciliationService`의 무제한 로드 패턴(페이지네이션
   없이 6만 건 로드)이라는 실제 버그를 코드 레벨로 확인했다.** 다만
   재검토 결과 이 버그가 차지하는 크기는 33MB 정도로, **384MB 힙을
   이것 하나로 채웠다고 단정할 근거는 없다**(3.2절) — 힙의 73%(262MB)를
   차지하는 byte[]/char[]/object[]의 실제 주인은 shallow-size 히스토그램
   만으로는 특정 못 했다. 그래도 이 버그는 페이지네이션 없이 무제한
   로드한다는 점에서 원인 여부와 무관하게 고쳐야 할 실제 결함이라 후속
   작업으로 분리해뒀다(3.5절).
4. **1000-tier는 여전히 위험권이다.** SSE 문제(브로드캐스트 포화)는 잡혔지만,
   힙 압박(정확한 지분은 미확정)과 알림 복구 배치의 확인된 버그가 남아있어
   추가 조치(청크 처리 적용, 가능하면 MAT 등으로 retained-size 재분석) 후
   재검증이 필요하다.
5. 축③(메모리/스왑) 전반은 4차 문서의 결론(384MB 유지, 스펙 문제로
   귀결)이 여전히 유효하되, **오늘은 "느린 GC"보다 "진짜 OOM"이 더
   심각한 형태로 나타났다** — 애플리케이션 코드의 확인된 버그(무제한
   배치 로드, 33MB어치)가 힙 압박의 "일부"를 스스로 만들고 있었다는 게
   새로 밝혀진 사실이고, 나머지 대부분(262MB)의 원인은 아직 미확정으로
   남는다.
